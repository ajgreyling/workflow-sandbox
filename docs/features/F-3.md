# F-3: User management — Spec

## Summary
Lets a user of the app capture people by name and surname, and see, edit and delete them, all from the home screen. Users are added and edited in a modal and stored in a local SQLite database, so they survive page reloads and app restarts.

## Requirements

### Home screen
1. The home screen is the page at `/`. If no home page exists yet (F-1 not done), this feature creates a minimal one with a visible heading.
2. The home screen shows an **Add user** button next to the existing controls. The F-2 toggle may be moved to make room, but must keep working.
3. Below the existing controls, the home screen shows a users table with the columns **Name** and **Surname**, and an **Edit** and a **Delete** button on each row.
4. The table lists all users, newest first, with no paging.
5. When there are no users, the text "No users yet." is shown in place of the table.

### Add
6. Clicking **Add user** opens a modal titled "Add user" with labelled **Name** and **Surname** text inputs and **Save** and **Cancel** buttons. The Name input has focus when the modal opens.
7. Saving valid input trims both values and stores exactly one new user (`id`, `name`, `surname`, `created_at` in UTC). The modal then closes, the new user appears at the top of the table, and "User <name> <surname> saved." is shown on the home screen.
8. Saving the same name and surname again creates another user. Duplicates are allowed.

### Edit
9. Clicking **Edit** on a row opens the same modal, titled "Edit user", with the inputs pre-filled with that user's values. It has the same validation and buttons as Add.
10. Saving valid input updates exactly that user with the trimmed values. The modal then closes, the table refreshes, and "User <name> <surname> updated." is shown.

### Delete
11. Clicking **Delete** on a row opens a confirmation dialog that asks "Delete <name> <surname>?" and has **Delete** and **Cancel** buttons.
12. **Cancel** closes the dialog and changes nothing. **Delete** removes exactly that user from the database and the table, and shows "User <name> <surname> deleted."

### Messages
13. The saved, updated and deleted messages are gone after a page reload.

### Validation and errors
14. Name and Surname are required. Each is trimmed and must then be 1–100 characters long. Any characters are allowed (e.g. "O'Brien", "José"). The rules are checked in the browser and on the server.
15. Invalid input shows an inline message under the field: "Name is required", "Surname is required", "Name must be 100 characters or fewer" or "Surname must be 100 characters or fewer". Each message is linked to its input for screen readers (`aria-describedby`). The modal stays open, and what the user typed is kept.
16. If saving fails (server or database error), the modal shows "Could not save user. Please try again." and keeps what the user typed.
17. If deleting fails, the dialog shows "Could not delete user. Please try again." and the user stays in the table.
18. The **Save** button is disabled while a save is in progress, so clicking it twice quickly stores only one user.
19. If the user being edited or deleted no longer exists (e.g. deleted in another tab), the app shows "This user no longer exists.", closes the modal or dialog, and refreshes the table.

### Modal behaviour and accessibility
20. **Cancel** or **Escape** closes the modal or dialog without saving.
21. While the modal or dialog is open, focus stays inside it. When it closes, focus returns to the button that opened it.
22. Pressing **Enter** in an input submits the form.
23. Names and surnames are always displayed as plain text, never interpreted as HTML.

### API
24. `GET /api/users` returns `200` with all users, newest first, as `[{"id", "name", "surname", "created_at"}]`.
25. `POST /api/users` with `{"name", "surname"}` returns `201` and the created user.
26. `PUT /api/users/{id}` with `{"name", "surname"}` returns `200` and the updated user.
27. `DELETE /api/users/{id}` returns `204`.
28. `PUT` and `DELETE` return `404` for an unknown `id`. `POST` and `PUT` return `422` for invalid input, using the same rules as requirement 14.

### Persistence
29. Users are stored in a SQLite database at `data/app.db` (git-ignored). The path can be overridden with the `APP_DB_PATH` environment variable, and tests use a temporary database.
30. The `users` table is created automatically on app startup if it doesn't exist.
31. Users survive a page reload and an app restart.

### Layout
32. The home screen, modal and dialog are usable without horizontal scrolling on mobile (375px and up), tablet and desktop.

## Decisions
- **Operations in scope:** Add, list, edit and delete. (user)
- **Home screen:** The page at `/`. This feature creates a minimal one if F-1 isn't done yet. (user)
- **Page rendering:** FastAPI serves Jinja2 templates, with a little vanilla JS for the modal. (user)
- **SQLite access:** Python's built-in `sqlite3` module, no ORM. (user)
- **Database location:** `data/app.db`, git-ignored, overridable with `APP_DB_PATH`. Tests use a temporary database. (user)
- **Schema creation:** On app startup, with `CREATE TABLE IF NOT EXISTS`. No migrations. (user)
- **Stored fields:** `id`, `name`, `surname`, `created_at` (UTC). (user)
- **Duplicates:** Allowed. Every save adds a new row. (user)
- **Button:** "Add user", on the home screen next to the existing controls. (user)
- **Form presentation:** A modal dialog on the home screen. (user)
- **Form controls:** Name and Surname inputs, Save and Cancel buttons. (user)
- **After save:** Close the modal and show "User <name> <surname> saved."; the message is gone after a reload. (user)
- **List location:** A users table on the home screen, below the existing controls. (user)
- **List columns and order:** Name, Surname, Edit and Delete buttons; newest first. (user)
- **Empty list:** Show "No users yet." (user)
- **Paging:** None; all users are shown. (user)
- **Edit form:** The same modal as Add, pre-filled and titled "Edit user". (user)
- **After edit:** Close the modal, refresh the list, show "User <name> <surname> updated." (user)
- **Delete confirmation:** "Delete <name> <surname>?" with Delete and Cancel. (user)
- **After delete:** Remove the row and show "User <name> <surname> deleted." (user)
- **API:** REST JSON at `/api/users` and `/api/users/{id}`; 201/200/204, 404 if missing, 422 if invalid. (user)
- **Validation:** Required, trimmed, 1–100 characters, any characters; checked in the browser and on the server. (user)
- **Invalid input:** Inline message under the field; the modal stays open and the input is kept. (user)
- **Save failure:** "Could not save user. Please try again."; the input is kept. (user)
- **Delete failure:** "Could not delete user. Please try again."; the user stays in the table. (recommended)
- **Over-length message text:** "Name/Surname must be 100 characters or fewer". (recommended)
- **Double submit:** Save is disabled while a save is in progress. (user)
- **Missing user on edit or delete:** "This user no longer exists."; close and refresh. (user)
- **Modal closing and focus:** Cancel and Escape close it; focus is trapped while open and returns to the opener on close. Clicking outside does not close it. (user)
- **Accessibility:** Labelled inputs, Name focused on open, Enter submits, errors linked to fields. (user)
- **Displaying names:** Always as plain text, never as HTML. (recommended)
- **Screen sizes:** Mobile (375px and up), tablet and desktop. (user)
- **Existing features:** The F-2 toggle may be moved to make room. (user)
- **Acceptance criteria:** The button opens the form. A valid save stores exactly one row with trimmed values and returns to home with the confirmation. Invalid input is blocked. Cancel saves nothing. The list shows all users in order. Edit and delete affect exactly one row. Data survives a reload and a restart. (user)

## Out of scope
- Paging, searching, filtering or re-sorting the list.
- Any user fields other than name and surname.
- Authentication or per-user data; all visitors see the same users.
- Database migrations.
- Bulk add, edit or delete.
